# AROMIN AI — Architecture Blueprint (Phase 0)

Status: design only. Nothing here is implemented. Items marked **[VERIFY]** depend on facts about third-party services that have not been confirmed and must be checked in Phase 1 before any code relies on them.

Scope rule: this is a standalone service. It does not read, modify, or depend on the AROMIN Dashboard code or the existing website chatbot. All future integration is through the public Agent API and outbound webhooks.

---

## 1. Executive Architecture

AROMIN AI is a single Python service (modular monolith) with two process types built from one codebase:

- **api**: FastAPI. Handles chat (SSE streaming), REST resources, inbound webhooks. Runs short agent turns inline.
- **worker**: runs durable tasks (multi-step jobs, follow-ups, memory extraction, ingestion, outbound webhooks, scheduled jobs).

State lives in **PostgreSQL** (source of truth for everything durable, including vectors via pgvector, the task queue, and the event outbox). **Redis** is used only for things that may be lost: cache, rate limits, SSE fan-out, session scratch state.

Core decisions:

| Decision | Choice |
|---|---|
| Shape | Modular monolith, 2 process types. Split into services only when a module has a different scaling or release need. |
| Agent loop | Own thin runtime (no agent framework). |
| LLM access | `LLMProvider` interface; Arvan adapter first, OpenAI-compatible adapter as generic fallback. |
| Durability | Every agent step checkpointed in Postgres; tasks resumable. |
| Safety | LLM only proposes tool calls. Policy engine + server-side scope binding decide what executes. |
| Numbers that matter | Prices, scores, routing are computed by code from data, never generated by the model. |

## 3. Agent Runtime Design

**AgentProfile** (config, versioned in DB): `name, system_prompt_id, model_tier, allowed_tools[], policy_set, max_steps, max_turn_seconds`.

**Turn loop** (one user message → one final reply):

```
1. load: conversation, rolling summary, customer profile, open task state
2. route (cheap model or rules): intent, needs_kb, needs_web, needs_customer_data, escalate?
3. context = ContextEngine.build(budget, route)
4. stream model call
5. if tool_calls:
     for each call: validate args (JSON Schema) → bind scope → PolicyEngine.check
        allow            → execute (timeout, retries per tool), parallel if independent
        require_approval → create Approval, return "pending" result to model
        deny             → return structured denial to model
     append compact results → checkpoint step → goto 3   (until max_steps, default 6)
6. final answer → persist message → emit message.sent → enqueue post-turn jobs
   (memory extraction, lead signal update, summary refresh)
```

**Escalation to a Task**: if the plan needs > `max_steps`, an external wait (approval, human, scheduled time) or exceeds `max_turn_seconds` (default 25s), the runtime creates a Task, replies with an acknowledgement, and the worker continues it.

**Reliability**

- Model calls: retry on 429/5xx/timeouts, exponential backoff with jitter, max 3; then fallback to the configured secondary model/provider. Never retry after partial tool side effects without an idempotency key.
- Tools: each call carries `idempotency_key = hash(task_id, step_no, tool, args)`; write tools must honor it.
- Timeouts: per tool (registry), per model call (default 60s), per turn.
- Checkpointing: each step (`model_request`, `tool_call`, `tool_result`, `model_response`) persisted in `task_steps`; a crashed turn resumes from the last completed step.
- Cancellation: `tasks.cancel_requested` checked between steps; in-flight tool allowed to finish (or cancelled if tool declares `cancellable`).
- Guards: loop detection (same tool+args twice → stop), token budget per turn, max cost per conversation/day.

Choice: own runtime (~1–2k LOC).
Why: the loop is simple; we need exact control of checkpoints, policy, scope binding, and token budgets; easy to debug and test with a fake provider.
Alternative: LangGraph / LangChain agents.
Why not: heavy abstractions, frequent API churn, harder to audit and to keep provider-independent; checkpointing model doesn't match our task tables.

## 4. Memory Architecture

| Layer | What | Where | Retrieved | Summarized | Retention |
|---|---|---|---|---|---|
| Conversation | All messages (role, content, channel, tool calls ids) | `messages` (Postgres) | Last K turns every call | Rolling summary when unsummarized turns exceed ~1.5k tokens (small model) | Raw 12 months (configurable), then summary only |
| Session | Ephemeral turn state: typing, stream cursor, pending UI events | Redis, TTL 30 min | During live session | No | TTL |
| Customer | Structured facts: business type (cafe/restaurant), branches, city, current software, team size, pain points, budget range, decision maker, preferred channel/time | `customer_facts` (key, value, confidence, source_message_id, updated_at) | When conversation is linked to a customer; compact profile ≤300 tokens | Facts are the summary | Until deletion request; facts expire if `confidence` low and stale > 6 months |
| Semantic | Embeddings of past conversation summaries and notable facts | `memory_embeddings` (pgvector) | Only when route says history is relevant (similarity ≥ threshold, top 3) | Created from conversation summaries | Same as customer |
| Task state | Plan, steps, tool results, status | `tasks`, `task_steps` | When resuming / continuing | Old step payloads compacted after completion | 90 days after completion, then pruned (audit log kept) |

**Writes to customer memory** happen post-turn in a background job: a small model proposes facts via `memory.propose_facts` (schema-validated); code applies them (higher confidence or newer wins; contradictions kept with both sources and flagged).

**Privacy controls**: phone numbers stored encrypted (app-level AES-GCM, key from secret store) plus a keyed hash (HMAC) for lookup; PII redaction in logs; `DELETE /v1/customers/{id}/data` erases messages, facts, embeddings (audit log keeps redacted entries); consent flag per customer and per channel (SMS opt-in/opt-out).

## 5. Context Management

The Context Engine fills a fixed token budget per call from prioritized slots. Each slot has a hard cap; lower-priority slots are dropped first.

| Priority | Slot | Cap (tokens, initial) | Included when |
|---|---|---|---|
| 1 | System prompt + agent profile | 700 | always (stable prefix, cache-friendly) |
| 2 | Tool definitions (only allowed tools for this route) | 800 | always; filtered by route |
| 3 | Active task state | 300 | open task |
| 4 | Customer profile (structured) | 300 | customer linked |
| 5 | Last K turns | 2,000 | always (K adaptive) |
| 6 | Rolling summary | 400 | older turns exist |
| 7 | KB chunks (with source ids) | 1,500 | `needs_kb` |
| 8 | Tool results this turn (compacted) | 1,500 | after tool calls |
| 9 | Web excerpts (with URLs) | 1,200 | `needs_web` |
| 10 | Semantic memory hits | 300 | relevance ≥ threshold |

Rules:

- Retrieval is conditional on the router; no KB/web/memory lookup for greetings, small talk, or answers already in context.
- Tools return compact structured outputs (≤ 1–2k chars). Large payloads are stored and the model gets a summary + reference id; it can request a slice with `artifact.read`.
- Stable prefix first (system, tool schema), volatile content last, so provider-side prompt caching works if available **[VERIFY Arvan support]**.
- Token counting with the target model's tokenizer when available, else a calibrated estimator. Persian text typically costs more tokens per word than English; caps are measured in tokens, not characters.
- Persian normalization before retrieval/embedding: unify Arabic ي/ك → ی/ک, normalize ZWNJ, digits (۰-۹ / ٠-٩ → canonical), strip diacritics.

## 6. Tool Architecture

**Registry entry**

```python
class ToolSpec(BaseModel):
    name: str                      # "crm.create_lead"
    description: str               # 1–2 lines, written for the model
    input_model: type[BaseModel]   # → JSON Schema for the model
    output_model: type[BaseModel]
    permissions: set[str]          # e.g. {"lead:write"}
    risk: Literal["read", "write", "external_comm", "financial", "destructive"]
    timeout_s: float
    retry: RetryPolicy             # attempts, backoff, retry_on
    idempotent: bool
    scope_params: set[str]         # params injected by server, hidden from model
    handler: Callable[[Ctx, BaseModel], Awaitable[BaseModel]]
```

Execution pipeline: `parse → validate input → inject scope params (customer_id, conversation_id, actor) → PolicyEngine → handler (timeout) → validate output → audit log → compact result to model`.

**Scope binding** (key security property): tools used in customer-facing conversations never accept `customer_id`/`conversation_id` from the model. The server injects them from the authenticated session, so a prompt-injected model cannot read or change another customer's data.

Initial tool set:

| Tool | Risk | Notes |
|---|---|---|
| `kb.search` | read | AROMIN knowledge, returns chunks + source ids |
| `web.search`, `web.fetch` | read | see §8 |
| `catalog.get_products`, `catalog.get_price` | read | prices only from here, never from model memory |
| `customer.get_profile`, `customer.update_facts` | read / write | scoped |
| `crm.create_lead`, `crm.update_lead` | write | |
| `sales.record_signals`, `sales.set_stage` | write | inputs to scoring |
| `sales.request_handoff` | write | creates handoff + notifies |
| `followup.schedule` | write | creates scheduled task, respects comm policy |
| `sms.send` | external_comm | policy: consent, quiet hours, daily cap |
| `quote.draft` | write | draft only; sending needs approval |
| `discount.propose` | financial | always `require_approval` above configured limit (default 0) |

No tool runs SQL text. Handlers use repository functions with fixed queries.

## 7. RAG Architecture

Three separate knowledge sources, never mixed in one index:

1. **AROMIN Knowledge** (products, FAQ, sales playbooks, training notes) → our RAG index.
2. **Live Business Data** (prices, stock, leads, salespeople) → tools only, never embedded (would go stale).
3. **Public Web** → §8, not stored except a short-lived cache.

**Pipeline** (worker jobs):

```
source (upload | URL | Arvan object storage bucket)
 → fetch → extract text (docx/pdf/html/md) → Persian normalize
 → chunk: heading-aware, ~400–600 tokens, 15% overlap; FAQ entries = 1 chunk each
 → embed (multilingual model) → upsert into kb_chunks
 → mark document version active; previous version inactive (kept for rollback)
```

- **Storage**: `kb_documents(id, source_uri, title, checksum, version, status, tags, lang)`, `kb_chunks(id, document_id, version, ord, text, heading_path, tokens, embedding vector(D), tsv)`.
- **Change detection**: checksum per source; re-ingest only changed documents. A scheduled job re-scans the bucket (this gives the "dynamic" KB without depending on Arvan's managed KB sync).
- **Retrieval**: hybrid = pgvector cosine (HNSW) top 20 + keyword (pg_trgm similarity on normalized text; Postgres has no Persian stemmer, so `simple` FTS + trigram) top 20 → reciprocal rank fusion → top 5. Metadata filters: `tags`, `product`, `status=active`.
- **Reranking**: not in v1. Add a cross-encoder or provider reranker only if eval shows retrieval misses.
- **Attribution**: every chunk passed to the model carries `[S1] title §heading`; the model must cite source ids; the API returns sources with the message.
- **Versioning**: embedding model + dimension stored per index version; changing embedding model = build a new index version, switch atomically.

Choice: own RAG in pgvector.
Why: control over chunking, Persian normalization, metadata filters, versioning, attribution; one database.
Alternative: Arvan managed Knowledge Base **[VERIFY API]**; dedicated vector DB (Qdrant).
Why not: managed KB gives less control over filters/versioning and is a lock-in point (can still be added behind the `Retriever` interface); Qdrant adds a service we don't need below a few million chunks.

## 8. Web Research Architecture

```
router: needs_web? (time-sensitive, outside AROMIN knowledge, explicit request)
 → web.search(query, k=5)           SearchProvider interface
 → select 2–3 results (model or heuristic)
 → web.fetch(url)                   httpx, timeout 10s, size cap 2 MB, robots respected
 → extract main text (trafilatura) → normalize → cap 1.2k tokens per page
 → model answers citing URLs
```

- `SearchProvider` adapters: SearXNG (self-hosted), and a commercial API (Brave/Tavily/other) **[VERIFY availability and payment from Iran]**. Start with whichever passes the Phase 1 check.
- Cache search results 1h and fetched pages 24h in Redis (key: normalized URL).
- `web_sources` recorded per message (url, title, fetched_at) for attribution and audit.
- Fetched content is **untrusted**: wrapped in delimiters, stripped of scripts, never able to change policy or tool permissions. Instructions inside web pages are ignored by design (tools enforce permissions regardless of model output).
- SSRF protection: block private/link-local IP ranges after DNS resolution, allow http/https only.

## 9. Task / Background Job Architecture

The Task Engine runs every unit of work that must survive a crash: agent turns, multi-step agent work, follow-ups, inbound SMS turns, memory extraction, ingestion and scheduled jobs. PostgreSQL is its only durable store (queue, step journal, schedules, side-effect ledger). Redis only carries progress notifications and rate-limit buckets, so losing Redis loses no task and no result. Full design: [Task Engine reference](aromin-ai-task-engine.md).

**Execution model: one engine, two hosts**

A task is a durable row in `tasks` plus an append-only step journal in `task_steps`. One `TaskRunner` executes it, and both process types host the runner with the same lease protocol:

| Mode | Runs in | Used for |
|---|---|---|
| Immediate | `api`, inside the request | Agent turn with a user waiting (§3 inline limits: 25 s, 6 steps) |
| Background | `worker` | Escalated turns, inbound SMS turns, post-turn jobs, API-submitted tasks |
| Scheduled | `worker` | Future `run_at` (follow-ups, reminders) and recurring jobs from `schedules` |

```
POST /v1/chat ─▶ txn: message + task row (running, owner api) ─▶ inline turn ─▶ reply
                                     │ exceeds limits / needs a wait / pod dies
                                     ▼
              tasks (queued/waiting, by lane) ◀─ claim (SKIP LOCKED) ─ worker slots ─▶ journal ─▶ deliver
                                     ▲                                                   │
SMS webhook / POST /v1/tasks / schedules ──────────────────────── outbox events, Redis progress, SSE
```

**Core principles**

- **Durable from the first moment.** Every agent turn gets its task row in the same transaction as the user's message, including turns with no tool calls. A crashed or redeployed API pod never drops a turn; its lease expires and a worker finishes it.
- **API → worker handoff.** An inline turn that exceeds its limits, needs a wait, or is interrupted by a deploy is escalated at a step boundary: the API hands over the lease (`running → queued/waiting`) and a worker continues from the journal. Completed steps never re-run, and a step with side effects is never interrupted. The user gets an acknowledgement, progress labels over SSE, and the final reply through the conversation stream.
- **Write-ahead step journal.** Each step is recorded before it runs and completed after. Model output (including tool arguments) is durable before any tool runs, so on resume the model is never re-asked for a decision it already made. Internal DB writes commit in the same transaction as step completion, so they happen exactly once.
- **Leases and fencing.** Workers claim with `SELECT … FOR UPDATE SKIP LOCKED`, hold a 60 s lease renewed by heartbeat, and every write is fenced by a `lease_token`. A reaper requeues expired leases; a stalled worker that wakes up after losing its lease can write nothing.
- **Idempotency.** Each step has a stable `idempotency_key` derived from task, generation and step number, fixed when the step is planned. Scheduled jobs, follow-ups, fallbacks and `POST /v1/tasks` (`Idempotency-Key`) use unique dedupe keys, so a repeat creates nothing new.
- **External side-effect ledger.** SMS sends and other external calls are recorded in `side_effects` before the call. A retry with the same key returns the stored result. If the outcome is unknown (timeout after the request left), the engine reconciles through provider dedupe or lookup, and otherwise parks the task for a person to resolve. It never blindly re-sends. Outbound webhooks use the §10 outbox: exactly-once enqueue, at-least-once delivery with a stable event id.
- **One active reply per conversation.** All turns of a conversation (inline, background and fallback) share `concurrency_key = conv:<id>`, enforced by a unique index on running tasks. A message that arrives during a turn is attached to the running owner, and a *deliver gate* re-plans before replying if the owner hasn't seen the newest message. The customer gets one coherent reply, never two parallel ones.

**Queues, priority and fairness**

| Lane | Work | Capacity rule |
|---|---|---|
| 0 interactive | Agent turns with a web user waiting | Own slots that no other lane can take |
| 1 customer | Inbound SMS turns, fallbacks, follow-ups, handoff/routing notifications | Own slots, with a per-replica reserve for inbound customer messages |
| 2 default | Memory extraction, summaries, lead scoring | Shared slots that also serve lanes 0–1 under load; not customer-facing, watched by a lag alert |
| 3 bulk | Ingestion, KB rescans, SMS campaigns, pruning | Separate `worker-bulk` container |

Spare capacity is lent only toward more urgent work. Inside a lane, ordering is FIFO by `run_at`. Per-kind caps, split SMS and LLM rate budgets, and spread-out wake times keep one burst (a 20,000-recipient campaign, 600 follow-ups after quiet hours) from delaying a customer who just wrote.

**Status lifecycle**

```
queued ─▶ running ─▶ succeeded | failed | cancelled | dead
  ▲          │  └─▶ waiting (approval | human | time) ─▶ queued / running
  └─ retry ──┘
failed / dead ─▶ queued   (operator retry only)
```

Transitions are enforced in code and by a DB trigger. `waiting` releases the slot and lease; a waiting task costs one row and wakes on a signal (approval decision, staff or customer reply) or at its timer or wait deadline.

**Retries, failures and fallback**

- **Two-level retry.** Short in-process retries per tool and model policy; then task-level requeue with exponential backoff and jitter, tuned per lane. Errors are classified (transient, dependency unavailable, outcome unknown, tool error, permanent, bug), and only some classes retry. A tool error is returned to the model, not treated as a task failure. Provider outages open circuit breakers and don't count toward dead-lettering.
- **Deadlines and budgets.** Stale work is not done late: agent turns have deadlines that count active time only (waits don't count), follow-ups have calendar deadlines, and background agents have step and cost budgets.
- **Dead-letter.** A task becomes `dead` after repeated consecutive failures, too many total failures, or repeated crash-loop lease expiries. `dead` is a status, not a separate table, so the journal and ledger stay in place for diagnosis. Operators can list, retry (optionally rewinding to a step) or resolve dead tasks.
- **Human-safe fallback.** Every transition into `failed` or `dead` inserts, in the same transaction, a `task.fallback` task. It posts a fixed Persian template message (works even during an LLM outage), opens a handoff to a salesperson, and on SMS sends the apology through the ledger. It obeys the one-reply rule and skips the apology if a later turn already answered.

**Cancellation.** `POST /v1/tasks/{id}/cancel` cancels queued and waiting tasks immediately; a running task gets `cancel_requested` and stops at the next step boundary. Model calls and pure tools are cancelled mid-flight. Writes and external calls already in flight finish and are recorded, so a cancel never creates an unknown SMS. Fan-out tasks (campaigns) cascade the cancel to their children. The result lists side effects that already happened.

**Scheduling.** One-off work is a task with a future `run_at` and a dedupe key; it re-checks consent, stage and quiet hours when it fires. Recurring jobs are defined in code and synced to a `schedules` table by the release job on every deploy and rollback. Every worker runs the scheduler tick, with no leader. A row lock, an atomic "insert task + advance `next_run_at`", and a slot-based unique key make duplicate runs impossible with any number of replicas.

**Worker recovery and deploys.** On crash, the reaper requeues expired leases and the next owner resumes from the journal; an unfinished external step is reconciled, never blindly repeated. On SIGTERM, workers and API pods stop claiming, let in-flight steps reach a boundary, and release their tasks without counting a failure. During rolling deploys, workers claim only `kind@version` values they support. Tasks that no live process can run are failed by a sweep (with fallback and alert) instead of waiting forever.

**Horizontal scale.** Any number of `api` and `worker` replicas can run: claims use `SKIP LOCKED`, wake-ups use `LISTEN/NOTIFY` with polling as fallback, and scheduling needs no leader. Capacity grows by adding replicas or slots per lane. Bulk work scales separately in `worker-bulk`. The design targets roughly 50k tasks/day and about 100 claims/s on one Postgres primary; beyond that, see §21.

**Observability.** Prometheus metrics for queue depth and lag per lane, throughput by status, step latency, retries by error class, waiting tasks, live workers, side-effect outcomes, schedules, breakers and cost. The `api` also computes queue gauges, so "no live worker" pages even when every worker is down. Structured logs carry `task_id`, `kind`, `lane`, `attempt`, `step_no` and `conversation_id`, never chain-of-thought or raw prompts. Alerts page on stalled interactive/customer lanes, no live workers, unknown SMS outcomes, dead or failed fallbacks, unclaimable tasks and reaper errors. A Grafana "Tasks" dashboard shows lag, throughput, latency and the dead list.

Choice: Postgres-backed queue (`SKIP LOCKED`) with our own runner, step journal and side-effect ledger.
Why: task state, queue state and domain writes commit in one transaction, with one source of truth and nothing lost on Redis eviction. Journaling, waits, fencing and the ledger are the hard part, and no off-the-shelf queue provides them.
Alternative: Procrastinate; Celery/Arq on Redis; Temporal.
Why not: Procrastinate covers claiming and retries but not journaling, waits or the ledger. Celery/Arq keep durable state in Redis (§1 forbids it), and Celery is sync-first. Temporal adds a cluster to operate; revisit it if task graphs become long-lived and branching.

Choice: lanes with reserved capacity and FIFO inside each lane.
Why: no customer-facing lane can be starved by another lane or by a burst of one kind, and FIFO is fair and fully index-supported.
Alternative: one queue ordered by numeric priority.
Why not: strict priority starves low priorities, aging needs a query the index can't serve, and a burst at equal priority still blocks everything else.

Choice: serialize all turns of a conversation and gate the reply.
Why: concurrent turns produce two inconsistent replies, each blind to the other's input. The cost is that an attached message waits for the owner's next step boundary, and the widget shows progress meanwhile.
Alternative: one concurrent turn per message, or cancel-and-restart on every new message.
Why not: the first gives double replies by default; the second discards completed work and can leave an SMS send in flight.

## 10. Event Architecture

**Transactional outbox**: domain code writes the event row in the same DB transaction as the change. A dispatcher in the worker delivers it.

Envelope:

```json
{ "id": "evt_01J…", "type": "lead.scored", "version": 1,
  "occurred_at": "2026-10-01T09:30:00Z",
  "subject": {"lead_id": "lead_…", "customer_id": "cus_…"},
  "data": { "score": 72, "breakdown": { "...": "..." } } }
```

Event types (v1): `message.received`, `message.sent`, `conversation.created`, `lead.created`, `lead.qualified`, `lead.scored`, `lead.assigned`, `followup.due`, `followup.sent`, `task.created`, `task.completed`, `task.failed`, `handoff.created`, `handoff.accepted`, `approval.requested`, `approval.resolved`.

Delivery:

- Internal handlers (e.g. `lead.scored` → routing) run in-process in the worker.
- Outbound webhooks to subscribers (Dashboard, n8n, CRM): `POST` with `X-Aromin-Signature: t=<ts>,v1=<HMAC-SHA256(secret, ts.body)>`, at-least-once, retries with backoff for 24h, then dead-letter; receivers dedupe by `id`.
- `webhook_subscriptions(id, url, secret_ref, event_types[], active)`.

Choice: Postgres outbox + webhooks.
Why: exactly matches our scale, no event loss, simple integration for n8n/Dashboard.
Alternative: Kafka / NATS / RabbitMQ.
Why not: operational overhead without a current need; the outbox can later publish to a broker without changing producers.

## 11. Sales Agent Architecture

The Sales Agent is an `AgentProfile` on the generic runtime plus sales tools and a stage model. It is not a separate runtime.

Stages (stored on the lead, changed only via `sales.set_stage`):

```
discovery → qualification → need_analysis → recommendation → objection_handling
          → closing (quote/demo) → handed_off | nurture | lost
```

Per stage, the profile injects a short stage instruction (≤150 tokens) instead of one large sales prompt.

| Capability | Mechanism |
|---|---|
| Discovery / need analysis | Model asks; facts saved via `customer.update_facts` |
| Qualification | Model records signals with evidence via `sales.record_signals`; code decides qualified |
| Product recommendation | `catalog.get_products` with filters from customer facts; model explains |
| Objection handling | KB playbook chunks (tag `objection:*`) retrieved by objection type |
| Lead creation | `crm.create_lead` once minimum fields exist (name or business + contact + need) |
| Scoring | Deterministic, see §12 |
| Routing | Rules engine, see §12 |
| Follow-up | `followup.schedule` → scheduled task → message via channel, policy-checked |
| Quote preparation | `quote.draft` from catalog prices; sending needs salesperson approval |
| Human handoff | `sales.request_handoff` (reason, summary) → agent stops replying in that conversation until released |

Handoff triggers: customer asks for a human, high score + closing stage, discount/contract request, negative sentiment ×2, low confidence ×2, policy denial on a needed action.

## 12. Lead / CRM Model

```
Customer 1─* Conversation 1─* Message
Customer 1─* Lead *─1 Salesperson
Lead 1─* LeadSignal          Lead 1─* LeadScore (history)
Lead 1─* FollowUp            Lead 1─* Task
Conversation 0..1─1 Lead     Handoff *─1 Conversation, *─1 Salesperson
```

**Signals** (one row per observation): `lead_id, signal (need|intent|budget|authority|timeline|fit|urgency|engagement), value (enum or 0–1), evidence_message_id, confidence, source (model|human|rule), created_at`.

**Scoring** (explainable, deterministic):

```
score = Σ weight[s] × normalize(latest value of s, discounted by confidence)  → 0..100
breakdown = [{signal, value, weight, contribution, evidence_message_id}]
```

- Weights live in `scoring_configs(version, weights jsonb, thresholds jsonb, active)` — no final weights hard-coded; start uniform, tune from outcomes.
- Every score row stores `config_version` and the full breakdown.
- Engagement is computed from data (reply latency, message count), not by the model.

**Routing** (rules, ordered, first match): explicit customer request → region (city/province) → product line → salesperson skills → capacity (open leads < max) → round-robin. Output includes the matched rule (explainable). Unassigned after N minutes → `lead.unassigned` alert.

## 13. Communication Architecture

```python
class Channel(Protocol):
    name: str                                   # "web", "sms", "whatsapp"
    async def parse_inbound(req) -> InboundMessage
    async def send(to: Address, msg: OutboundMessage) -> DeliveryResult
    capabilities: ChannelCaps                   # streaming, max_len, media, rich
```

- **Website chat**: streaming capable; responses streamed via SSE.
- **SMS**: non-streaming. Runtime produces a final answer; channel formatter shortens (SMS segment limits, Persian uses UCS-2 → fewer chars per segment), strips markdown, splits if needed.

SMS flow:

```
SMS provider → POST /v1/webhooks/sms/{provider}
 → verify (signature or shared secret + IP allowlist, per provider) → dedupe by provider msg id
 → resolve customer by phone HMAC → find/open conversation (channel=sms)
 → opt-out keyword? → mark opt-out, confirm, stop
 → enqueue agent turn (background; SMS has no latency requirement)
 → PolicyEngine (quiet hours, daily cap, consent) → SmsProvider.send → delivery report webhook
```

`SmsProvider` adapters for Iranian providers (e.g. Kavenegar, SMS.ir) **[VERIFY APIs, webhook signing, delivery reports]**.

Choice: SSE for website chat.
Why: traffic is server→client streaming; client sends messages with normal POST; works over HTTP/1.1 and HTTP/2, through CDNs/proxies, auto-reconnect with `Last-Event-ID`.
Alternative: WebSocket.
Why not: needs sticky connections and its own auth/heartbeat handling, with no current need for bidirectional streaming. Revisit for voice. **[VERIFY Arvan CDN does not buffer `text/event-stream`; otherwise bypass CDN for the stream path.]**

## 14. Security Architecture

| Area | Design |
|---|---|
| Server-to-server auth | API keys (`ak_live_…`), stored as SHA-256 hash, scoped to roles, rotatable, last-used tracking |
| Staff auth | Email + password (argon2id) issuing short-lived JWT (15 min) + refresh token; OIDC later |
| Website visitors | Widget obtains an anonymous visitor JWT (24h) from `POST /v1/widget/session` with a public widget key + Origin allowlist; token is bound to one visitor/conversation |
| RBAC | `admin`, `sales_manager`, `salesperson`, `service` (Dashboard/n8n), `visitor`; permission strings checked in API and in tools |
| Webhooks in | HMAC signature + timestamp (±5 min) or provider mechanism; replay protection by message id |
| Webhooks out | HMAC-SHA256 per subscription secret |
| Rate limiting | Redis token bucket per API key, per visitor, per phone, per IP; separate budget for LLM cost per conversation/day |
| Secrets | Environment / secret store of the host platform **[VERIFY Arvan secret management]**; never in DB plaintext, never in prompts, never in logs |
| Data access | LLM has no DB access; tools use fixed repository queries; scope params injected server-side |
| Approvals | `approvals(id, action, payload, requested_by, status, decided_by, decided_at)`; `require_approval` actions only execute after `approval.resolved=approved` |
| Audit | Append-only `audit_log` for every tool call, approval, auth event, data export/delete (PII redacted) |
| Prompt injection | Untrusted content (web, KB, customer text) delimited; permissions enforced in code, independent of model output |
| Tenancy | Single tenant (AROMIN). Per-customer isolation via scope binding. No `org_id` (see §21) |

Hard prohibitions (enforced in code, not prompt): no arbitrary SQL, no raw credentials to the model, no permission bypass, no secret exposure, no destructive operations (bulk delete, data export) from the agent.

**Business policy layer** (`policy_sets`, versioned):

```yaml
tools: {allow: [...], deny: [...]}
discount: {max_percent_without_approval: 0}
financial_actions: require_approval
contracts: human_only
communication:
  sms_quiet_hours: "21:00-09:00 Asia/Tehran"
  sms_max_per_customer_per_day: 2
  require_opt_in: true
privacy:
  never_disclose: [other_customers, internal_costs, salesperson_phone]
```

class LLMProvider(Protocol):

## 16. API Contract Design

Conventions: base `/v1`; JSON; `Authorization: Bearer <api key | JWT>`; `Idempotency-Key` on POST; errors as RFC 9457 `application/problem+json`; cursor pagination (`?cursor=&limit=`); ids are prefixed ULIDs (`conv_`, `msg_`, `lead_`, `task_`).

```
POST /v1/widget/session           → {visitor_token, expires_at}
POST /v1/conversations            {channel, customer_ref?, metadata?} → Conversation
GET  /v1/conversations/{id}       → Conversation + messages (paginated)
POST /v1/chat                     {conversation_id?, message, client_msg_id, channel}
     Accept: application/json     → {conversation_id, message, sources[], task_id?}
     Accept: text/event-stream    → SSE:
        event: message.delta      data: {"text": "..."}
        event: tool.started       data: {"tool": "kb.search", "call_id": "..."}   (display-safe name only)
        event: tool.completed     data: {"call_id": "...", "ok": true}
        event: message.completed  data: {"message_id": "...", "sources": [...], "task_id": null}
        event: error              data: problem+json
POST /v1/tasks                    {kind, input, run_at?} → Task (202)
GET  /v1/tasks/{id}               → Task {status, progress, result?, error?}
POST /v1/tasks/{id}/cancel        → Task
POST /v1/leads                    {customer, source, notes?} → Lead
GET  /v1/leads/{id}               → Lead + latest score + signals
POST /v1/leads/{id}/qualify       → {qualified, missing_fields[], reasons[]}
POST /v1/leads/{id}/score         → LeadScore {score, config_version, breakdown[]}
POST /v1/leads/{id}/assign        {salesperson_id?} (empty = run routing) → {salesperson_id, rule}
POST /v1/handoff                  {conversation_id, reason, salesperson_id?} → Handoff
POST /v1/handoff/{id}/release     → returns conversation to the agent
POST /v1/approvals/{id}/decide    {decision: approve|reject, note?}
POST /v1/webhooks/sms/{provider}  provider payload → 200 (fast ack, async processing)
POST /v1/webhook-subscriptions    {url, event_types[]} → {id, secret}
GET  /health                      liveness
GET  /ready                       DB + Redis reachable
```

Internal reasoning is never returned or logged; only final messages, tool names, and sources.

## 21. Risks and Trade-offs

| Risk / trade-off | Impact | Mitigation |
|---|---|---|
| Arvan model capabilities unknown (tool calling, streaming, Persian quality) | Core loop may need a fallback mode | Phase 1 spike; JSON-mode tool fallback; provider interface allows switching |
| Model invents prices/features | Wrong commitments to customers | Prices only from `catalog.*` tools; evals check; policy forbids price text without tool result |
| Prompt injection via web/KB/customer text | Unauthorized actions | Permissions in code, scope binding, approvals for risky actions, injection evals |
| Availability of foreign services from Iran (search APIs, SaaS monitoring) | Features blocked | Self-hostable defaults (SearXNG, GlitchTip, Prometheus) |
| Persian token cost | Higher spend | Tight context budgets, summaries, model routing, caching |
| Own runtime instead of framework | Maintenance burden | Keep it small, heavily tested; frameworks remain an option behind same interfaces |
| Postgres does many jobs | Single point of failure, contention at high scale | Managed/backed-up Postgres, read replicas later; outbox/queue can move to a broker without API changes |
| No multi-tenancy | Re-work if AROMIN serves other businesses | Decision accepted now; adding `org_id` later is a known migration |
| SMS spam/regulatory issues | Blocking, complaints | Consent, opt-out, quiet hours, daily caps, audit |
| Memory extraction errors | Wrong customer facts | Confidence + evidence per fact; salespeople can correct; contradictions flagged |
